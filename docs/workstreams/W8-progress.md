### WU19. 병렬 처리량 천장. 꼬리였고, 남은 것은 우리 고정비이며, 그것은 유지합니다

결과 문서는 `docs/perf/parallel.md` 입니다.

**WU18 이 남긴 열린 질문을 닫았습니다.** occupancy 가 100%→29% 로 무너지던 것이 **전적으로 꼬리**였습니다. 직렬 판정 200ms 초과인 쌍 **4개(279개 중)** 를 빼면 occupancy 가 모든 워커 수에서 93% 이상으로 유지됩니다. 코드는 아무것도 안 바뀌었습니다.

**꼬리를 뺀 스케일링은 최고 7.23배(12 워커)입니다.** 3회 반복 최소값으로 판정당 25.46 → 12.91 → 6.97 → 4.13 → **3.52** → 3.78 ms 입니다. 조율자 회신이 인용한 6.13배는 제가 status 로 먼저 올린 단일 통과분이고, 반복 최소값으로는 7.23배입니다. 최고점이 12 워커인 것은 이 기계의 물리 코어 수와 같고 `baseline.md` 가 합성 쌍에서 찾은 모양과 같습니다. **단일 통과로는 6.1~6.7배 사이에서 흔들려 없는 추세를 만들 수 있으므로 최소 3회로 보고합니다.**

**GIL 은 무관합니다.** `bindings/python/src/quodlibet_module.c:337` 과 `:481` 이 판정 전체를 `Py_BEGIN_ALLOW_THREADS` 로 감쌉니다.

**남은 비선형은 우리 고정비입니다.** solver 왕복을 무결성 해시 / 프로세스 기동 / Bitwuzla 실행으로 쪼갰습니다. 1→16 워커 배율이 각각 3.51배, 4.46배, **1.71배** 입니다. **16 워커에서 무결성 해시(14.07ms)가 Bitwuzla 자신의 중앙값 실행(13.40ms)보다 큽니다.** 1 워커에서도 해시+기동이 판정 중앙값의 39%, 16 워커에서 47% 입니다.

**해시 대상 확인(조율자 요청).** 질의도 solver 상태도 아니고 **Bitwuzla 바이너리 identity** 이며 세션 수명 동안 불변입니다(`src/solver.c:1707`). 질의 digest 는 따로 있고 메모리에서 SMT-LIB 텍스트에 대해 계산하는 싼 것입니다(`:2260`). **그런데 그 불변성이 검증을 줄일 근거가 되지 못합니다.** `execve` 는 매 spawn 마다 디스크에서 로드하므로 확립해야 하는 것이 "이 값이 아직 그 값인가" 가 아니라 "커널이 지금 로드할 파일이 아직 기록된 바이트인가" 이고, 그것은 캐시된 답으로 설 수 없습니다.

**(b) 4회를 3회로 줄이기는 채택하지 않았습니다. 조율자가 준 기준(결과 동치)이 성립하지 않습니다.** 통제는 exec 하나당 직전·직후 검증 쌍이고 판정은 exec 이 둘이라 넷입니다.

```
H1  exec1  H2   ...   H3  exec2  H4  -> 판정 반환
```

`H2` 와 `H3` 사이에 exec 이 없어 `H3` 이 중복으로 보이지만, `H3` 을 빼면 **`H2` 이후에 변조되고 `H4` 이전에 복원되는 변조**를 놓칩니다. 지금은 `H3` 이 잡습니다. **그 구간에 `exec2` 가 들어 있습니다.** 반대로 `H2` 를 빼는 것은 `exec1` 이 이미 낸 답을 지키는 검증을 빼는 것이라 더 나쁩니다. 그래서 **넷이 exec 둘에 대한 bracket 의 최소**이고, 이것은 취향이 아니라 반례로 보인 것입니다.

이 bracket 이 무엇을 약속하고 무엇을 약속하지 않는지도 적어 두었습니다. 사후 해시를 넘겨 지속되는 변조는 잡고, 파일에 쓸 수 있고 복원 시점을 맞출 수 있는 공격자는 4회로도 못 막습니다. 축소 논증은 그 기준에 대고 평가해야 하며 위 반례가 그렇게 한 것입니다.

**(a) 현행 유지가 결론입니다.** (c) 는 조율자가 반려했습니다. 프로세스 기동도 격리 계약 자체라 그대로 둡니다. 이 단위는 고침 없이 규명과 가격표로 닫습니다.

**CTest 직렬.** windows-clang **507/507**, linux-clang **506/506**. 계측은 전부 플래그 뒤이고 정본 빌드는 코드가 같습니다.

### WU18. 판정 하나의 단계별 분해. 답은 "전부 solver" 입니다

`docs/perf/baseline.md` 가 판정당 총량은 말하면서 그 안을 못 말한다고 적어 둔 구멍을 메웠습니다. 결과 문서는 `docs/perf/stages.md` 입니다.

**방법은 프로파일러가 아니라 계측입니다.** 브리프의 두 선택지 중 골랐고 근거가 있습니다. 이 호스트에서 VTune 은 자식 프로세스를 띄우는 워크로드에서 매달리고(수집 종류가 아니라 자식이 가른다는 것은 이미 확인해 둔 사실), 판정은 매번 Bitwuzla 를 fork 합니다. **VM 을 기다릴 일이 아니라 프로파일러를 안 쓰면 되는 일이었습니다.** baseline 의 "VM 대기" 판단을 이 근거로 정정했습니다.

`src/stage_timer.h` 를 만들었습니다. `QL_STAGE_TIMING` 이 정의될 때만 컴파일되고, 꺼지면 매크로가 전부 사라져 클록 호출도 분기도 저장소도 없습니다. **훅은 경계에만 있고 루프 안에는 하나도 없어서** C 가 아무리 커도 판정당 클록 호출 수가 고정입니다. `CMakeLists.txt` 는 조율자 소유라 안 고쳤고, 헤더 하나로 끝내면서 저장소를 정확히 한 TU(`src/proof_smt.c`)가 갖게 했습니다.

**W1 소유 파일에는 훅이 파일당 한 곳씩입니다.** `src/c_frontend.c` 와 `src/c_lower.c` 의 `ql_c_parser_parse` 호출을 감싼 것뿐입니다. 그것 없이는 파싱을 프런트엔드/로어링과 분리할 수 없습니다. 로직은 안 건드렸습니다. `src/product.c` 에는 SMT-LIB 렌더 지점 세 곳에 훅이 있습니다.

**표본은 val 1,049개 중 실제로 로어링되어 판정에 도달하는 244개입니다**(브리프가 말한 251 과 같은 자리). 나머지는 지원하지 않는 C 라 method 에 도달조차 못 하므로 분모에서 뺐습니다. 넣으면 단계가 돌지도 않은 판정으로 나누는 것이 됩니다.

**결과.**

| 단계 | 중앙값 ms | p90 ms | 평균 비중 |
|---|---|---|---|
| 파싱 + 프런트엔드 + 로어링 + IR + miter + 직렬화 전부 | **0.378** | | **0.6%** |
| solver 왕복 | **12.842** | 45.776 | **98.8%** |
| method 합계 | 13.334 | 47.054 | 100% |

**총합이 맞습니다.** method 평균 62.923 ms + method 밖 1.253 ms = 판정당 실측 64.176 ms. 미계측 잔차 0.064 ms(0.1%).

**이것이 baseline 의 우선순위를 정정합니다.** 귀속 분석이 `emit_store`(50.3%)와 `ql_ir_builder_destroy`(21.6%)를 다음 표적으로 지목했는데, **그것은 `coverage` 도구 안에서 맞고 판정 안에서는 로어링 전체가 0.3% 입니다.** 두 워크로드는 같은 우선순위 목록을 쓰면 안 됩니다. 중복 파스 제거도 판정 경로에서는 0.13% 라 넣을 이유가 없습니다.

**정본 성능 불변을 두 번 쟀습니다.** 판정 워크로드에서 A(계측 전 main) 62.623 / B(이 브랜치 정본) 62.157 / C(계측) 62.956 ms 최소값으로, 셋이 서로의 산포 안이고 순위가 라운드마다 뒤집힙니다. **그래서 이 표만으로 "오버헤드 없음" 이라고 말하면 잡음을 읽는 것입니다.** solver 분산이 비 solver 단계 전부보다 크기 때문입니다. 그래서 훅이 드러날 수 있는 자리에서 다시 쟀습니다. solver 가 없고 유닛마다 두 훅이 도는 `coverage` 경로에서 정본 299 ms 대 계측 296 ms 이고 **digest 가 3681642204 로 같습니다.** 계측 쪽이 1% 빠르게 나오는데 그것이 산포입니다.

**병렬 구간은 실제로 병렬로 돕니다. 다만 천장이 경합이 아니라 꼬리입니다.** 2 워커에서 1.86배에 점유율 100% 입니다. 최고점은 12 워커 2.73배이고 물리 코어 수와 같습니다. 워커를 늘리면 판정당 in-thread 시간이 67.0 → 111.8 ms 로 늘고 **그 증가의 83% 가 solver 왕복**입니다. 우리 단계도 상대적으로는 더 많이 부풀지만(파싱 4배, 로어링 6배) 절대값이 0.17 ms 에서 시작해 다 합쳐도 2 ms 미만입니다.

**CTest 직렬.** windows-clang **503/503**, linux-clang **502/502**. 계측 빌드(`linux-stage`)도 같은 소스에서 컴파일됩니다. 시험 수가 늘어난 것은 이 단위와 무관한 다른 워크스트림의 것이고 W8 은 시험을 더하지 않았습니다.

**점유율이 28% 까지 떨어지는 것은 경합이 아닙니다.** 244개 중 한 판정이 5~6.7초 걸리고, **12 워커에서 그 하나가 배치 벽시계의 96.0%** 입니다. 배치는 가장 느린 구성원보다 빨리 끝날 수 없으므로 나머지 워커가 그것을 기다리며 놉니다. solver 의 평균(62.2 ms)이 p90(45.8 ms)보다 크다는 분포가 같은 말을 합니다. **소수 질의가 배치를 끌고 갑니다.** 그래서 `baseline.md` 의 465 pairs/s(합성 쌍, solver 시간 균일)와 여기의 2.73배는 둘 다 맞고 서로 다른 입력에 대한 것입니다. 남는 레버는 병렬성이 아니라 스케줄링(긴 것 먼저)이고, 그것은 배치 API 소유자의 판단이라 여기서는 사실만 세워 둡니다.

### WU17. G8 퍼징 캠페인. 크래시-0 이 아니고, 이유가 하나입니다

WSL Ubuntu-24.04 에서 `linux-fuzz` 프리셋(`QL_BUILD_FUZZERS=ON`, ASan+UBSan+libFuzzer)으로 빌드하고 `scripts/coordinator/fuzz-campaign.sh` 로 타깃당 60초 유계 캠페인을 돌렸습니다. clang 18.1.8, glibc 2.39 이라 **Bitwuzla 번들의 GLIBC_2.38 요구는 걸리지 않았고 툴체인에서 막힌 곳은 없습니다.**

**`/mnt/c` 가 아니라 WSL 네이티브 경로(`~/ql-fuzz`)로 트리를 복사해 거기서 빌드하고 돌렸습니다.** 브리프가 허용한 경로이고, WU6 에서 이미 같은 것을 겪었습니다. 9p 변환이 빌드와 퍼저 자신의 파일 I/O를 다 먹습니다. `fuzz-campaign.sh` 가 `out/build/linux-fuzz` 를 자기 위치 기준으로 잡으므로 사본과 캠페인이 같은 트리에 있으면 경로는 저절로 맞습니다.

**타깃은 9개입니다.** 브리프의 "11개" 는 `tests/fuzz/` 의 헤더 둘(`fuzz_targets.h`, `fuzz_contract_targets.h`)을 같이 센 수로 보입니다. CMake 의 GLOB 은 `fuzz_*.c` 만 잡으므로 실제 실행 타깃은 9개입니다.

**결과: 7 클린, 2 크래시.** 전체 벽시계 약 7분. 타깃별 수치는 `docs/fuzz/campaign-20260810.md` 에 표로 있습니다.

**크래시 둘은 같은 결함 하나입니다.**

```text
fuzz_policy         -> ql_policy_parse        src/policy.c:650
fuzz_policy_result  -> ql_policy_result_parse src/policy.c:1196
ASan heap-buffer-overflow, READ of size 2, strlen 안
```

두 함수 모두 `if (json_size == 0u) { json_size = strlen(json); }` 라는 **문서화되지 않은 sentinel** 을 가지고 있습니다. 포인터+길이 계약대로 길이 0 인 non-NUL-terminated 슬라이스를 주면 할당 밖을 읽습니다. `include/quodlibet/policy.h` 에는 이 편의 규약이 한 줄도 적혀 있지 않고, `ql_precondition_parse`, `ql_problem_open`, `ql_source_signature_open` 은 길이를 준 대로 씁니다. **나머지 일곱 타깃이 같은 빈 입력에서 멀쩡한 이유가 그것입니다.** 저장소 전체에서 이 패턴은 `src/policy.c` 의 이 두 곳뿐입니다.

**입력 최소화는 할 것이 없습니다. 빈 입력이 곧 최소입니다.** 한 바이트도 필요 없습니다. libFuzzer 가 입력을 정확히 그 크기로 할당하므로 변이도 조작된 바이트도 필요 없이 첫 실행에서 죽습니다.

**처음에는 고치지 않고 status 로 올렸습니다.** `src/policy.c` 가 W8 소유가 아니었기 때문입니다. **조율자가 수정을 W8 에 라우팅했습니다**(W3 정리, W1 은 로어링이라 충돌 없음). 아래가 그 수정입니다.

#### 수정: sentinel 을 지웠습니다. 호출자가 그렇게 정했습니다

취향이 아니라 **호출자 실측**으로 갈랐습니다. 두 함수의 모든 사용처를 훑으면 이렇습니다.

- **유일한 프로덕션 호출자 `bindings/python/src/ql_check.c:390` 은 sentinel 에 안 기댑니다.** `quodlibet_module.c` 가 `s#` 로 포인터와 길이를 같이 받아 `spec->policy_json_size` 에 넣습니다. sentinel 에 닿는 유일한 경우인 `policy_json=""` 은 길이 0 이고 `strlen` 도 0 이라 **전에도 파스 오류였고 지금도 파스 오류입니다.** 동작이 안 바뀝니다.
- `tests/test_fuzz_contracts.cpp` 는 `std::strlen` 을 명시합니다.
- `tests/test_policy.cpp` 의 네 곳만 리터럴에 `0u` 를 넘겼습니다. 그 넷을 `std::strlen` 으로 고쳤습니다.

**아무도 그 편의에 기대지 않으니 남길 이유가 공개 헤더에 함정을 문서화하는 것뿐입니다.** 그래서 지웠습니다. `include/quodlibet/policy.h` 에 이 파서들이 원래 `ql_precondition_parse` 및 artifact 디코더와 공유하던 규칙을 명시했습니다. `json_size` 는 읽을 바이트 수이고, 그 너머는 안 읽고, 길이 0 은 빈 문서라 `QL_STATUS_PARSE_ERROR` 로 거절합니다.

**빈 입력을 유효한 정책으로 승격하지 않습니다.** 거절이고, 수정 전에도 거절이었습니다. 바뀐 것은 그 답에 도달하는 길에 있던 OOB read 가 사라진 것과, **NUL 종단이 없는 버퍼에서도 그 답이 성립하게 된 것**입니다.

- 시드 `tests/fuzz/corpus/policy/empty-input`, `tests/fuzz/corpus/policy_result/empty-input`.
- `FuzzContracts.PolicyTargetsSurviveAnEmptyInput` 이 두 시드를 libFuzzer 드라이버와 **같은 타깃 본문**으로 리플레이합니다. 매 ctest 마다 돕니다.
- `Policy.ParserRejectsAnEmptyDocumentWithoutReadingThePointer` 와 그 result 짝. **NUL 이 하나도 없는 1바이트 힙 버퍼**를 넘겨서, 길이 너머를 읽으면 sanitizer 가 잡는 heap overflow 가 되게 했습니다. 이 형태가 아니면 시험이 조용히 통과합니다.
- `Policy.ParsersStopAtTheLengthTheyWereGiven`. 유효한 문서 뒤에 쓰레기를 붙이고 종단을 안 붙입니다. 파서가 길이 대신 포인터를 재면 깨집니다.

**처음 커밋(`b4d3243`)에서는 이 시드들을 결정적 캠페인 목록에 일부러 넣지 않았습니다.** 고칠 권한이 없는 결함으로 ctest 관문을 빨갛게 만들면 다른 워크스트림의 검증을 막기 때문입니다. 수정을 라우팅받은 지금은 넣는 것이 맞아서 넣었습니다.

**시험이 실제로 결함을 잡는지 확인했습니다.** sentinel 을 도로 넣고 다시 빌드하니 넷 중 **셋이 실패**합니다(`PolicyTargetsSurviveAnEmptyInput`, 두 `EmptyDocument` 시험). 되돌리니 넷 다 통과합니다. **`ParsersStopAtTheLengthTheyWereGiven` 은 양쪽에서 통과합니다.** 길이가 0 이 아닐 때 파서가 길이를 지키는 것은 원래 성립하던 성질이라, 이 시험은 결함 재현이 아니라 계약을 못질하는 것입니다. 재현하지 않는 시험을 재현한다고 적지 않습니다.

**재캠페인 결과: 9/9 크래시-0.** 전 타깃이 `DONE` 에 도달했고 `ERROR:`/`SUMMARY:` 줄이 하나도 없으며 `crash-*` 산출물도 남지 않았습니다. 타깃별 수치는 `docs/fuzz/campaign-20260810.md` 표에 있습니다.

**CTest 직렬.** windows-clang **501/501**, linux-fuzz(ASan+UBSan+libFuzzer) **500/500**. 개수 차이는 Windows 에만 등록되는 파이썬 바인딩 시험 하나입니다(WSL 사본에 pytest 가 없어 그쪽에서 미등록).

**부수 관찰(고치지 않음, `scripts/coordinator/` 는 W8 소유가 아닙니다).** `fuzz-campaign.sh` 9행의 `code=$?` 는 `tail` 로 끝나는 파이프라인의 종료코드를 읽습니다. 그래서 **이번 크래시 둘도 로그에 `exit=0` 으로 찍혔습니다.** 크래시 판정을 종료코드로 하면 안 되고 `ERROR:`/`SUMMARY:` 줄로 해야 합니다. 이것 자체가 "크래시-0 을 실측했다" 는 주장을 조용히 위조할 수 있는 자리라 조율자에게 같이 올렸습니다.

### WU16. 반려 원인은 시험이 아니라 빌드였습니다

조율자가 `624d988` 을 반려했습니다. `test_a_check_spec_can_carry_a_session` 이 `CheckSpec` 에 `session` 키워드가 없다며 `TypeError` 로 실패한다는 것이었는데, 소스에는 그 필드가 분명히 있었습니다.

**원인은 빌드가 파이썬 파일을 안 옮기는 것이었습니다.** `bindings/python/CMakeLists.txt` 가 `__init__.py` 복사를 `_quodlibet` 타깃의 `POST_BUILD` 로 걸어 두었습니다. `__init__.py` 는 그 타깃의 입력이 아니므로, **파이썬만 고치면 확장이 다시 링크될 이유가 없고 복사도 안 돌아갑니다.** 실측으로 확인했습니다. `__init__.py` 에 한 줄 넣고 빌드하면 `ninja: no work to do` 가 나오고 패키지 안 파일은 예전 것 그대로입니다.

**제 실행에서 통과한 이유도 이것으로 설명됩니다.** 같은 세션에서 C 소스도 고쳤기 때문에 확장이 다시 링크되었고 복사가 딸려 돌았습니다. 파이썬만 고친 증분 빌드에서는 안 돕니다.

**이것이 제 시험 하나보다 큽니다.** 바인딩 시험이 소스가 아닌 예전 코드를 조용히 시험할 수 있다는 뜻이고, **틀린 이유로 통과하는 시험 스위트는 실패하는 것보다 나쁩니다.**

**수정.** 패키지 안 파일을 `POST_BUILD` 부산물이 아니라 **소스 파일에 의존하는 출력**으로 만들었습니다(`add_custom_command(OUTPUT ... DEPENDS ...)` + `ALL` 타깃).

**실측으로 확인한 것은 이것입니다.** 수정 전에는 `__init__.py` 만 고치면 `ninja: no work to do` 가 나오고 패키지 안 파일에 그 변경이 없습니다. 수정 후에는 같은 편집에 `Staging the quodlibet Python package` 가 돌고 변경이 들어갑니다.

이미 낡아 있는 패키지를 다음 빌드가 복구하는지도 재 보려 했는데 **그 실험은 제가 잘못 짰습니다.** 패키지 파일을 손으로 덮어쓰면 mtime 이 새것이 되어 ninja 가 최신으로 보는 것이 맞고, 빌드 산출물을 밖에서 건드린 경우까지 빌드가 감지해야 하는 것은 아닙니다. **확인하지 못했으므로 주장하지 않습니다.** 실제 문제였던 경로(소스만 고쳤을 때 안 따라오는 것)는 위에서 확인했습니다.

### WU15. 단발 `check()` 의 세션화

**선택적 세션 인자 자체는 세션 단위(WU12)에서 이미 들어가 있었습니다.** 이번 단위는 그것을 **실제로 쓸 수 있게** 만든 것입니다. 있는데 닿을 수 없거나 아무도 모르면 없는 것과 같습니다.

- **`CheckSpec` 이 세션을 나릅니다**(`as_kwargs()` 포함). 그전에는 spec 을 만들어 쓰는 호출자가 빠른 경로에 닿을 방법이 아예 없었습니다. 필드는 맨 뒤에 붙여 위치 인자 구성은 그대로입니다.
- **`check()` 와 모듈 docstring 이 세션을 말합니다.** 수치(1,093.8 ms 대 66.2 ms)와 예제를 같이 적었습니다.
- **암묵 기본 세션은 만들지 않았습니다.** 세션이 계약상 스레드 비안전이라 암묵 공유는 그 계약과 정면으로 부딪칩니다. 지시대로 명시적으로만 받습니다.

**시험 넷.** 세션 유무가 같은 판정을 내는 왕복(조건 1, WU12 에 이미 있던 것), 서로 다른 결론을 오가도 세션이 상태를 안 나름, `CheckSpec` 경로, 재사용이 실제로 빠름(조건 3). 마지막은 시간이 아니라 순서를 넉넉한 여유와 함께 봅니다.

**수치는 `docs/perf/baseline.md` 의 최적화 6번에 적었습니다**(조건 2).

### WU14. 예산 마감 양자화. 처방이 원인을 잘못 짚었습니다

지시받은 처방은 "남은 total budget 을 solver deadline 에 min 전파" 였습니다. **원인이 그것이 아니었습니다.**

- **solver 마감만 1 ms 로 줘도 판정이 1.1초 걸립니다.** solver 가 0.41초를 쓰는 것이 아닙니다.
- **원인은 판정당 backend 설치**(4.49MB 복사 + 해시 네 번 + 버전 프로브)이고, 판정 하나가 solver 를 두 번 부르므로 그것을 두 번 합니다.
- **이미 있는 세션이 그것을 지웁니다.** 10 ms 예산이 537 ms → **16.3 ms**, 100 ms 예산이 467 ms → **108.5 ms**. 마감이 지연에 비례하게 됩니다.

min 전파는 넣었지만 **측정 가능한 성능 차이가 없습니다**(10/20/30 ms 예산에서 전파 유무가 잡음 안). 이 슬라이스에서 solver 는 20~30 ms 에 답해 단계 경계 검사가 이미 촘촘합니다. 그래서 **성능 항목이 아니라 자원 한도 계약 항목으로 적었습니다.** 총 예산만 좁게 준 호출자가 solver 축 기본값만큼의 마감을 받는 구멍을 막는 것이고, 어려운 질의에서만 드러납니다. 계약은 시험 셋으로 고정했습니다.

`docs/perf/concurrency.md` 의 "두 solver 왕복" 이라는 읽기를 정정해 두었습니다.

CTest: windows-clang 476/476, linux-clang 475/475, linux-sanitize 475/475.

파이썬 쪽에서 "좁히기만 한다" 를 잡으려던 시험 하나는 접었습니다. `solver_timeout_ms=1` 이면 `unknown` 일 것이라 가정했는데 이 쌍은 1 ms 로도 풀립니다. **전제가 틀린 시험이지 코드가 틀린 것이 아니어서**, 검증 가능한 층(run context 가 남은 시간을 정확히 나른다)의 시험 셋만 남겼습니다.

## 지난 작업 단위 (WU12, 세션 객체)

### (B) 설계 (조율자 승인 형태 (2) 명시적 세션 객체)

**목표.** 판정마다 하던 스냅샷 복사 + 생성 시 해시 + 버전 프로브를 워커당 한 번으로 줄입니다. per-check 무결성 해시 두 번은 판정마다 그대로 돕니다.

**승인 조건 다섯.**

1. 세션 옵션 구조체에 `struct_size` + `abi_version`, append-only 규약
2. 세션은 계약상 스레드 비안전, 워커당 하나. 문서와 시험에 박기
3. 세션 생성 시 snapshot digest 를 세션에 기록. per-check 무결성 해시 두 번과 envelope 의 판정별 digest 기록은 유지
4. 세션 해제가 결정적으로 스냅샷을 지우는지 시험으로
5. bindings 의 `check_batch` 이전까지 이 단위에 포함

**배선 경로 (확인한 것).**

- `ql_solver_descriptor_v1` (`include/quodlibet/solver.h:155`) 은 `struct_size` 와 `void *reserved[8]` 이 있어 append-only 로 넓힐 수 있습니다. 여기에 세션을 받는 create 콜백을 더합니다.
- `ql_run_context_v1` (`include/quodlibet/method.h:33`) 도 `struct_size` 와 `reserved[8]` 이 있고, **`run_check` (`src/proof_smt.c:359`) 가 이미 이 context 를 받습니다.** 세션 핸들을 여기에 실어 내리면 pipeline 과 method 시그니처를 안 바꿉니다. 이것이 가장 짧은 건전한 경로입니다.
- `ql_check` (`bindings/python/src/ql_check.c`) 가 판정마다 registry 를 새로 만드는 지점이 재사용의 반대편입니다. 파이썬 쪽에 세션 객체를 노출하고 `check(session=...)` 로 받아 context 에 실어야 합니다.

**작업 순서.** 각 단계를 따로 커밋하고 각각 검증합니다. 중간에 끊겨도 브랜치가 성한 상태로 남습니다.

1. 코어: `ql_solver_session` 타입과 옵션 구조체, create/destroy, 스냅샷 소유 이전. 어댑터 안에서만 쓰고 시험 추가 (조건 1, 3, 4)
2. 배선: `ql_run_context_v1` 에 세션 필드 append, `run_check` 가 있으면 재사용
3. bindings: 파이썬 세션 객체와 `check_batch` 이전 (조건 5)
4. 측정: 판정당 before/after 와 `ETXTBSY` 잔존 재측정

**진행: 네 단계 전부 완료.**

- **1단계 코어.** `ql_solver_session` 과 옵션 구조체(`struct_size`+`abi_version`), create/destroy, `ql_solver_create_in_session`, `ql_solver_session_backend_digest`. descriptor 는 `reserved[8]` 을 typed 콜백 셋 + `reserved[5]` 로 바꿔 크기와 기존 필드가 그대로이고, 새 필드는 `struct_size` 로 가려 읽으므로 옛 descriptor 도 계속 통과합니다. 어댑터 쪽은 설치(`ql_bitwuzla_install`)를 state 에서 분리해 세션이 소유하거나 state 가 소유하거나 둘 중 하나가 되게 했습니다.
- **2단계 배선.** `ql_run_context_v1` 에 `solver_session` 을 reserved 한 칸에서 append 하고, `ql_pipeline_set_solver_session` 으로 파이프라인이 실어 내립니다. `run_check` 는 세션이 있으면 빌리고 없으면 예전대로 자기 것을 만듭니다.
- **3단계 bindings.** 확장이 abi3 라 새 heap type 대신 capsule 로 넘깁니다. 파이썬은 `quodlibet.SolverSession` (context manager, `close()`, 닫힌 세션 사용은 `ValueError`)이고 `check_batch` 는 thread-local 로 **워커마다 하나**를 엽니다. 세션을 못 여는 backend 에서는 조용히 예전 경로로 돕니다.
- **4단계 측정.** 아래.

**승인 조건 다섯 대응.** (1) 옵션 구조체 ABI: `OptionsInitStampsTheAbiContract`, `RejectsOptionsFromAnIncompatibleAbi`. (2) 스레드 비안전 워커당 하나: 헤더와 docstring 에 명시, `EachThreadGetsItsOwnSessionAndInstallation` 과 `test_check_batch_gives_every_worker_its_own_session`. (3) 세션 digest 기록 + per-check 해시 두 번 + envelope 판정별 digest: `ManySolversShareOneSnapshotAndItsDigest`, `test_a_session_does_not_change_the_verdict_or_the_digest`. (4) 결정적 해제: `DestroyingTheSessionRemovesItsSnapshot`. (5) `check_batch` 이전: 완료.

**효과.** 판정당 22.07 → 9.79 ms (**-55.6%**, 1 워커에서 번갈아 5회). `check_batch` 최고 처리량 229.5 → **465.3 pairs/s** (8 워커, 판정당 2.15ms). 그리고 **`ETXTBSY` 잔존이 7/2,304 에서 0/2,304 로 사라졌습니다** — 예측대로 스냅샷 쓰기가 판정당에서 워커당으로 바뀌어 창의 개수가 배치 크기만큼 줄었기 때문입니다.

**예상 3~4ms 였는데 12.3ms 가 나온 이유.** 예상은 복사와 생성 해시만 셌는데 세션은 **버전 프로브 서브프로세스**도 지웁니다. 모형에 없던 항목입니다. BLAKE3 때와 같은 방향의 오차이고 같은 교훈입니다. 모형은 하한입니다.

### WU8. 동시성 SIGSEGV 수정 (조율자 승인 후 위임받아 구현)

- **검증(조율자 승인 관문, 48쌍 16워커 10회, 다른 조건 동일한 두 트리): 수정 전 크래시 10/10, 수정 후 0/10.**

- **별건 발견: `ETXTBSY`.** 크래시가 사라지자 판정 48개 중 한둘이 `text file is busy` 로 실패하는 것이 보입니다. 스냅샷 쓰기 기술자에 `O_CLOEXEC` 이 없어(`src/solver.c:1907`) 다른 스레드의 fork/exec 가 물려받는 고전적 경쟁입니다. 제 수정이 만든 것이 아니라 크래시에 가려져 있던 것이며, BLAKE3 가 빨라져 창이 좁아지면서 겹침이 늘어 드러났습니다. 조율자에게 별도로 올렸습니다.

### WU9. `ETXTBSY` 수정 (조율자 위임)

- `open_binary_read` 와 `open_binary_write` 를 POSIX 에서 `open(..., O_CLOEXEC)` + `fdopen`, Windows 에서 `fopen` 모드 `N` 으로 바꿨습니다. **연 뒤에 플래그를 세우지 않습니다.** 그 사이에 fork 가 끼어들 수 있습니다.
- 지시대로 **스폰 재시도는 넣지 않았습니다.** 재시도를 먼저 넣으면 상속 차단이 실제로 됐는지가 가려집니다.
- `O_CLOEXEC` 가 POSIX.1-2008 이라 이 translation unit 만 `_POSIX_C_SOURCE` 를 200809L 로 올렸습니다(`src/log.c` 의 `_GNU_SOURCE` 처리와 같은 모양).
- **확장 관문 통과: 48쌍 16워커 10회에서 크래시 0, solver 시작 실패 0, 정상 10/10.**
- 배치 최고 처리량 229.5 pairs/s (8 워커, 판정당 4.36 ms).

### WU11. 확장 한계 위치와 `ETXTBSY` 잔존

- **처리량 최고점은 10 워커(251.3 pairs/s)이고 12 를 넘으면 내려갑니다. 이 기계의 물리 코어가 12 입니다**(논리 24). 이 워크로드는 물리 코어에서 포화하고 SMT 형제는 보태지 않습니다. 추측이 아니라 측정입니다.

## 설계 결정

### 짧은 수집은 가지별 비율을 못 준다

0.38s 실행은 표본이 90개 남짓입니다. 첫 수집에서 로어링의 파스가 52%, 프런트엔드의 파스가 18% 로 나와 같은 일이 3배 비싼 것처럼 보였습니다. 유닛 목록을 10회 이어붙여 4.48s 로 늘리자 두 가지가 30.0% 와 31.7% 로 대칭이 되었습니다. **앞의 비대칭은 표본 부족이었습니다.** 유닛당 비용은 반복으로 바뀌지 않으므로 이 늘리기는 공짜입니다. `vtune-hotspots.sh` 의 기본 반복이 10인 이유입니다.

### 회귀 관문은 프로파일러를 요구하지 않는다

VTune 은 WSL 이나 VM 에서만 살아 있고 수집에 수십 초가 듭니다. 회귀를 매번 그걸로 재면 아무도 안 잽니다. `bench-coverage.sh` 는 wall-clock 5회 최소값만 재고 어디서든 돕니다. 대신 **coverage JSON 의 digest 를 같이 찍어서**, 빨라진 것과 덜 한 것을 구분합니다. digest 가 바뀌면 시간 비교는 무효입니다.

### A/B 는 번갈아 재야 한다

coverage 읽기 경로를 잴 때 before 를 7회 몰아 돌리고 after 를 7회 몰아 돌렸더니 첫 시도는 -2.2%, 두 번째 시도는 +1.4% 로 **부호가 뒤집혔습니다.** 두 묶음 사이의 기계 드리프트가 1% 짜리 차이보다 큽니다. 번갈아 12회씩 돌린 최소값은 -1.09% 로 안정적이고 5회차부터 순위가 안 바뀌었습니다. **1% 급 변화를 주장하려면 번갈아 재야 합니다.**

### 평탄한 self time 은 상한이지 예산이 아니다

VTune 이 `fseek` 에 2.9% 를 붙였는데 lseek 두 번을 지운 실측 이득은 1.09% 였습니다. self time 에는 제거할 수 없는 몫(함수 진입, 버퍼 회계)이 섞여 있습니다. **프로파일 수치를 기대 이득으로 바로 쓰지 않습니다.** 이 워크스트림은 모든 최적화를 프로파일로 고르고 벤치로 확정합니다.

### 귀속은 상한다

`docs/perf/baseline.md` 에 파싱 61.6% 라고 적어 두고 그 위에 "약 30% 를 얻는다" 는 기대를 세웠습니다. 그 사이 W1 이 로어링을 넓혔고, 같은 코퍼스에 같은 명령이 유닛당 3배 무거운 다른 프로그램이 되었습니다. 지금 파싱은 18.7% 이고 기대치는 5% 였어야 합니다. **최적화를 고르기 전에 프로파일을 다시 뜹니다.** 문서에 적힌 비율은 그때의 사실이지 지금의 사실이 아닙니다. 병렬로 도는 워크스트림이 같은 코드를 넓히는 동안에는 특히 그렇습니다.

### 안 된 것도 적는다

W1 의 새 API 적용은 이득이 0 이었고, 넣지 않고 그 사실을 `docs/perf/baseline.md` 의 "시도했고 넣지 않은 것" 에 수치와 이유까지 적었습니다. **다음 사람이 같은 것을 다시 시도하지 않게 하려는 것이고, 그 이유가 곧 W1 에 필요한 요청의 내용이기도 합니다.** 성공한 최적화만 적으면 그 정보가 사라집니다.

### 프로브는 자기가 재는 프로그램과 같게 빌드해야 한다

`bench-snapshot.sh` 는 프로브를 라이브러리와 같은 portable BLAKE3 로 빌드했습니다. 라이브러리가 어셈블리로 바뀌자 **프로브만 옛 빌드로 남아 16.9ms 라는 이미 틀린 값을 계속 찍었습니다.** 프로브 빌드를 라이브러리 쪽에 맞추고, 전후 비교용으로 `QL_PROBE_PORTABLE=1` 을 남겼습니다. 측정 도구가 대상과 다르게 빌드되면 그 도구는 다른 프로그램을 재는 것입니다.

### 모형은 모형의 몫만 말한다

스냅샷 프로브는 해시 네 번만 모형화하므로 어셈블리 전환의 이득을 12.5ms 로 예측했습니다. 판정 전체 실측은 25ms 였습니다. **BLAKE3 가 스냅샷만이 아니라 이 프로젝트의 영속 identity 해시 전부**여서(`src/hash.c`) artifact digest 도 같이 빨라지기 때문입니다. 예측보다 좋게 나온 것이지만, 반대 방향으로 틀렸을 수도 있는 같은 종류의 오차입니다. **프로브 수치와 전체 수치를 따로 적습니다.**

### 대조군은 무엇을 끊었는지가 아니라 무엇이 남았는지로 세야 한다

WU5 에서 스레드와 프로세스가 같은 대역에서 멈추는 것을 보고 "공유를 전부 끊었는데도 그러니 천장은 solver 와 기계의 것" 이라고 읽었습니다. **틀렸습니다.** 인터프리터도 할당자도 코어 전역도 안 나눴지만, 둘 다 같은 9p 파일시스템으로 같은 5MB 실행 파일을 판정마다 복사하고 있었습니다. 가장 비싼 공유가 그대로 남아 있었습니다. 네이티브로 옮기니 처리량이 2.8배가 되고 확장이 4.65배에서 7.4배가 됩니다. **대조군을 세울 때 끊은 목록을 세지 말고 남은 것을 세야 합니다.**

### 확장 한계 수치는 대조군 없이는 뜻이 없다

`check_batch` 4.65배가 나쁜 것인지 좋은 것인지는 이 기계가 우리 종류의 일에 얼마를 주는지 모르면 판정할 수 없습니다. "24 코어니까 24배가 나와야 한다" 는 근거 없는 기준이고, 실제로 논리 24 코어는 물리 12 코어 + SMT 입니다. 그래서 우리 코드가 경합할 것이 아무것도 없는 구성(독립 프로세스 K개)을 같은 기계 같은 순간에 재서 천장을 먼저 세웠습니다. **10.97배 대 4.65배.** 이 대조가 있어야 "격차는 우리 것" 이라고 말할 수 있습니다.

### 점유율과 speedup 은 같이 봐야 한다

`check_batch` 는 16 워커에서 점유율 98% 인데 speedup 은 4.67배입니다. 점유율만 보면 "잘 병렬화되고 있다", speedup 만 보면 "풀이 놀고 있다" 로 잘못 읽힙니다. 둘을 같이 보면 답이 하나로 좁혀집니다. **스레드는 바쁘고, 바쁜 채로 각자 더 오래 걸린다.** 그래서 `bench-batch.py` 는 판정당 시간을 두 지표 옆에 같이 찍습니다.

### VTune 을 막는 것은 수집 종류가 아니라 자식 프로세스다

인수 시 기록은 "hotspots 는 되고 threading 은 안 된다" 였습니다. 배치 워크로드에 **hotspots** 를 걸어 보니 똑같이 매달렸습니다(무출력, 손으로 `pkill` 해야 끝남). coverage 워크로드는 hotspots 가 정상입니다. **가르는 것은 자식 프로세스입니다.** 판정마다 Bitwuzla 를 띄우기 때문입니다. 이 호스트에서 prove 경로의 함수 단위 프로파일은 못 얻습니다. VM 이 필요한 이유가 threading 리포트 하나가 아니라 prove 경로 전체입니다.

### 제거 가능한 몫은 46% 이고 파스 절반이 아니다

인수 문서는 "파싱 비용 절반" 을 말했지만 귀속을 보면 중복은 파스만이 아닙니다. 프런트엔드와 로어링이 각각 파서를 만들고, 각각 파싱하고, 각각 같은 방식으로 트리를 걸어 **필드가 글자 그대로 같은 노드 배열**(`ql_c_syntax_record` = `lower_node`)을 만들고, 각각 트리를 해제합니다. 파스 61.6% + 걷기 24.0% + 트리 해제 4.4% + 파서 생성 1.9% 중 절반이 중복이므로 약 46% 입니다. 실제 분석은 1.3%, 실제 로어링은 1.7% 입니다.

### threading 리포트는 두 환경에서 모두 못 얻었습니다

- **이 호스트(WSL).** 자식 프로세스를 띄우는 워크로드에서 수집기가 무출력으로 매달립니다. threading 만이 아니라 hotspots 도 같습니다. 가르는 것은 수집 종류가 아니라 자식 프로세스입니다.

1. **점유율 98%** (16 워커). GIL 은 판정 내내 풀려 있고 풀이 노는 것이 아닙니다.
2. **독립 프로세스 대조군.** 이 기계가 우리 종류의 일에 주는 천장을 따로 세웠습니다.
3. **스레드 대 프로세스.** 공유를 전부 끊어도 같은 대역에서 멈추는지 확인했습니다.
4. **확장 한계 위치.** 물리 코어 12 에서 포화하고 SMT 형제는 보태지 않습니다.

## 남은 단위 제안: 단발 `check()` 가 판정마다 backend 를 새로 세웁니다

세션은 `check_batch` 만 씁니다. **단발 `check()` 는 여전히 판정당 설치(4.49MB 복사 + 해시 네 번 + 버전 프로브)를 두 번 합니다**(판정 하나가 solver 를 두 번 부르므로).

| | 판정당 (Windows, 7회 최소) |
|---|---|
| `check()` 세션 없이 | **1,093.8 ms** |
| `check()` 세션 주고 | **66.2 ms** |
| 비 | **16.5x** |

**G6 의 "최대한 속도를 뽑는다" 에서 지금 남은 가장 큰 단일 항목입니다.** 채점기가 `check_batch` 를 쓰면 이미 이득을 받지만, 문서화된 단발 진입점을 그대로 쓰는 호출자는 16배를 손해 봅니다.

**설계 판단이 필요해 착수하지 않았습니다.** 암묵 기본 세션을 두면 수명이 문제입니다. 프로세스 전역이면 언제 해제하며, 스레드 로컬이면 스레드가 죽을 때 임시 디렉터리가 남습니다. 그리고 세션은 계약상 스레드 비안전이라 암묵 공유는 그 계약과 정면으로 부딪칩니다. 후보는 셋입니다.

1. **스레드 로컬 지연 생성 + `atexit`/FLS 정리.** 계약은 지키지만 정리 실패가 조용한 누수입니다.
2. **`check()` 에 세션을 넘기도록 문서와 예제만 고칩니다.** 안전하지만 기본 경로는 그대로 느립니다.
3. **그대로 둡니다.** 단발 호출은 원래 드물다고 보는 쪽입니다.

저는 2 를 먼저 하고(비용 0, 즉시 효과), 1 은 실제로 단발 호출이 병목이라는 사용례가 나오면 하는 쪽을 권합니다.
