# Fuzz campaign 2026-08-10

A bounded libFuzzer campaign over every `tests/fuzz/fuzz_*.c` target, run to
settle the G8 exit condition ("fuzz the parser, the lowering, the IR decoder
and the precondition parser, and reach zero crashes").

The campaign was run twice. The first run found one defect, on two targets. The
second run, after the fix, is **crash-free on all nine targets**.

## How it was run

Host: WSL2 Ubuntu-24.04 on Windows 11, clang 18.1.8, glibc 2.39, ninja.
`-fsanitize=fuzzer` is Clang/Linux only, so this cannot be run from the Windows
side of the checkout.

```sh
cmake --preset linux-fuzz          # QL_BUILD_FUZZERS=ON, ASan+UBSan+fuzzer
cmake --build --preset linux-fuzz --parallel
scripts/coordinator/fuzz-campaign.sh
```

The campaign was run from a copy of the worktree on a WSL-native path rather
than through `/mnt/c`, because the `/mnt/c` translation layer dominates both
build time and the fuzzer's own file I/O. Nothing in the build depends on the
location; `fuzz-campaign.sh` resolves `out/build/linux-fuzz` relative to
itself, so the copy and the campaign stay consistent.

Each target gets `-max_total_time=60` under a `timeout 70` guard. Wall clock for
a full campaign is about 9 minutes.

To replay just the two seeds this campaign added:

```sh
out/build/linux-fuzz/fuzz_policy        tests/fuzz/corpus/policy        -runs=0
out/build/linux-fuzz/fuzz_policy_result tests/fuzz/corpus/policy_result -runs=0
```

## What the first run found

`fuzz_policy` and `fuzz_policy_result` both died in their first execution, on
the empty input. One defect, two call sites:

```text
fuzz_policy         -> ql_policy_parse        src/policy.c:650
fuzz_policy_result  -> ql_policy_result_parse src/policy.c:1196
AddressSanitizer: heap-buffer-overflow, READ of size 2, inside strlen
```

Both functions carried an undocumented sentinel:

```c
if (json_size == 0u) {
    json_size = strlen(json);
}
```

A caller that honoured the pointer-plus-length signature and passed a
zero-length slice of a buffer that is not NUL-terminated got a read past the
end of the allocation. libFuzzer allocates each input to its exact size, so the
empty input was enough, with no mutation and no crafted bytes.

### Why it was fixed by deleting the sentinel

The callers decided it, not a preference. Grepping every use of both functions
across the tree finds:

- `bindings/python/src/ql_check.c:390`, the only production caller, passes
  `spec->policy_json_size`, which `quodlibet_module.c` fills from the `s#`
  argument alongside the pointer. It never relies on the sentinel: the one case
  that reaches it, `policy_json=""`, is a zero-length string whose `strlen` is
  also zero, so it was already a parse error and still is.
- `tests/test_fuzz_contracts.cpp` passes `std::strlen` explicitly.
- Four sites in `tests/test_policy.cpp` passed `0u` with C string literals.
  Those now pass `std::strlen` too.

So nothing needed the convenience, and keeping it would have meant documenting
a footgun in the public header. `include/quodlibet/policy.h` now states the
rule these parsers already shared with `ql_precondition_parse` and the artifact
decoders: `json_size` is the number of bytes to read, nothing past it is read,
and a zero length is an empty document rejected with `QL_STATUS_PARSE_ERROR`.

An empty input is not promoted to a valid policy. It is rejected, which is what
it was before the fix as well; the fix removes the out-of-bounds read on the
way to that answer, and makes the answer hold for a buffer with no terminator.

### Regression cover

- `tests/fuzz/corpus/policy/empty-input` and
  `tests/fuzz/corpus/policy_result/empty-input`, the seeds themselves.
- `FuzzContracts.PolicyTargetsSurviveAnEmptyInput` replays both through the
  same target bodies the libFuzzer drivers use, so it runs on every ctest.
- `Policy.ParserRejectsAnEmptyDocumentWithoutReadingThePointer` and its
  `ResultParser` twin pass a one-byte heap buffer that contains no NUL, so a
  read past the given length is a heap overflow the sanitizer build catches.
- `Policy.ParsersStopAtTheLengthTheyWereGiven` passes a valid document followed
  by trailing garbage and no terminator, which fails if a parser ever measures
  the pointer instead of honouring the length.

## Note on the campaign script

`scripts/coordinator/fuzz-campaign.sh` reads `$?` after a pipeline that ends in
`tail`, so the `exit=` it prints is `tail`'s status. In the first run it printed
`exit=0` for both crashing targets. Read the `ERROR:`/`SUMMARY:` lines and check
for leftover `crash-*` artifacts, not the printed exit code, until that is
corrected. The script is owned by the coordinator, so it is reported rather than
changed here.
