# asm2c-03 확인 계획 (G7)

작성 2026-08-10. 아직 실행 전. 실행 기록은 이 문서 아래에 같은 커밋 흐름으로 이어 적는다.

## 묻는 것

Quodlibet 이 asm2c 의 채점기와 강화학습기 환경(RTX PRO 6000 x8, Linux)에서 실제로 돌아가는가. **확인 수준으로 충분하며 장시간 학습이나 평가를 돌리지 않는다**(GOAL G7).

## 언제 실행하는가

W4 파이썬 바인딩이 main 에 통합된 직후. 바인딩 없이 VM 을 먼저 빌리면 채점기 경로를 확인할 수 없어 대여 시간만 늘어난다. Linux 네이티브 검증은 이미 WSL 에서 239/239 로 통과했으므로(2026-08-10) VM 없이 확인될 것은 남아 있지 않다.

## 접는 조건

- SPOT 재고가 두 존 연속 없으면 그 시점에 멈추고 기록한다. 재시도 루프를 돌리지 않는다
- vendor/build 가 VM 에서 30분 안에 안 끝나면 원인만 기록하고 접는다
- 채점기 경로에서 쌍당 지연 중앙값이 측정 불가능하게 나오면(크래시 등) 그 진단만 남기고 접는다
- **어느 경우에도 대여 시간 2시간을 넘기지 않는다.** 그 안에 못 끝내면 지우고 기록을 남긴다

## 절차

1. 생성: `MACHINE=g4-standard-384 bash scripts/cloud/asm2c_m8_fleet.sh create asm2c-03` (machine-model 루트에서. SPOT, gpu-training 태그, 존 로테이션 포함)
2. 성공 판정은 `instances list` 가 아니라 상태가 `RUNNING` 인지까지 본다 (VM_INDEX 규칙)
3. `bash scripts/local/gcpssh.sh up` 후 `gssh asm2c-03` 경로 사용
4. 소스 전송: 로컬 트리를 `git archive` 로 tar 해서 `gscp` (private repo 라 clone 대신. `out/` 제외)
5. `cmake --preset linux-clang && build && ctest`, 이어서 `linux-sanitize`
6. 파이썬 바인딩 `pip install .`, import, 판정 세 종류 왕복
7. **채점기 경로**: val 코퍼스 표본 N=100 쌍을 `check_batch` 로 걸어 쌍당 지연 분포(중앙값, p90)를 기록
8. **강화학습기 경로 스모크**: 8 GPU 에 작은 torch 행렬곱 루프를 띄워 둔 채 같은 머신에서 `check_batch` 를 병행하고 서로 방해 없이 끝나는지만 본다. 몇 분 이내
9. 기록을 이 문서에 적고 `gcloud compute instances delete` 로 지운다. 지운 것까지 기록한다

## 예상 비용

`g4-standard-384` SPOT 시간당 요금 x 최대 2시간. asm2c-02 와 같은 종류이므로 재고가 있는 존은 europe-west4 계열이 유력하다.

## 하지 않는 것

- 학습 실행, 체크포인트 로드, 60k 스텝 같은 것 전부
- asm2c-02 (학습 중) 접속이나 간섭
- VM 위 결과를 정본으로 삼는 것. 정본 수치는 이 문서에 적힌 것이다

## 결과 (2026-08-10, 실측)

VM: `asm2c-03`, `europe-west4-b`, `gkl-gpu`, `g4-standard-384` SPOT, RTX PRO 6000 Blackwell Server Edition x8 (97887 MiB each). 검증 드라이버는 `docs/vm/asm2c-03-verify.sh` 를 이미지 제약에 맞게 고친 판을 VM 의 `/tmp/verify2.sh` 로 올려 실행했다. 실행 완료 22:51:49 - 22:53:52 UTC.

### 이미지 제약 두 가지 (원래 드라이버가 전부 실패한 원인)

1. **Bitwuzla 실행 불가.** 이미지가 Ubuntu 22.04 (glibc 2.35, `GLIBCXX_3.4.30`) 인데 vendored `third_party/bitwuzla-linux-x86_64/bin/bitwuzla` 0.9.1 은 `GLIBC_2.38` 과 `GLIBCXX_3.4.32` 를 요구한다. `third_party/CMakeLists.txt:92` 의 runnable 검사에서 configure 가 죽어 stage 2 부터 전부 무너졌다. 남은 시간 안에 소스 빌드는 불가능해 **모든 stage 를 `-DQL_ENABLE_BITWUZLA=OFF` 로 돌렸다.** 따라서 이번 실행은 SMT 백엔드 없는 구성의 측정이다.
2. **`python3.11-dev` 부재.** 헤더가 없어 `find_package(Python ... Development.SABIModule)` 가 실패하고 `_quodlibet` 타깃 자체가 정의되지 않아 `ninja: error: unknown target '_quodlibet'` 로 wheel 빌드가 죽었다. `apt-get install python3.11-dev` 후 해결.

### 판정

- **네이티브 코어와 파이썬 바인딩이 Linux x86_64 에서 빌드되고 303/303 통과한다는 것은 확인됐다.** 8 GPU 부하와 `check_batch` 병행이 서로 방해하지 않는다는 stage 8 목표도 확인됐다 (모든 장치 활성, 두 작업 모두 완주).
- **채점기 쌍당 지연 수치는 정본으로 쓸 수 없다.** solver 가 없어 80%가 error, 20%가 unknown 으로 즉시 반환된 것이라 median 0ms 는 실제 검증 비용이 아니다. 계획서 7번 항목(쌍당 지연 분포)은 **미달성**이다.
- 다음에 같은 측정을 하려면 VM 이미지를 Ubuntu 24.04 로 잡거나 Bitwuzla 를 대상 이미지에서 빌드해 vendoring 해야 한다. 그리고 프로비저닝 단계에 `python3.11-dev` 를 넣어야 한다.

### stage 5 진단: CUDA context 가 있는 프로세스에서 `check_batch` 가 SEGV 한다

`rl_smoke.py` 가 SIGSEGV(139) 로 죽었다. GPU 부하 스레드와 무관하게, **같은 프로세스에 CUDA context 만 올라와 있으면 재현된다.** 최소 재현으로 잘라 확인한 결과는 이렇다.

| 조건 | 결과 |
| --- | --- |
| `check_batch(workers=1)`, CUDA 없음 | 8/8 정상 |
| `check_batch(workers=8)`, CUDA 없음 | **8/8 정상** |
| `check_batch(workers=8)`, CUDA context 있음 | **8회 중 3회 SEGV** (간헐적) |

core dump backtrace 는 solver 프로세스 생성 경로를 가리킨다.

```
#0  ... in _quodlibet.abi3.so
#1  <signal handler called>
#2  __GI___libc_read (nbytes=4, buf=..., fd=156)      <- libuv 의 child error pipe
#4  uv_spawn ()
#7  ql_solver_create ()
#12 start_thread
```

즉 `src/solver.c:1680` 의 `uv_spawn` 이 fork 하는 구간이다. libuv 의 fork+exec 경로는 CUDA 가 등록한 atfork 처리와 겹칠 때 안전하지 않고, worker 를 여러 개 띄워 동시에 spawn 할 때만 터지므로 경합이다. **강화학습기 프로세스 안에서 채점기를 직접 호출하는 설계는 이 상태로는 못 쓴다.** 채점기를 별도 프로세스로 떼거나 spawn 을 직렬화/전용 스레드로 몰아야 한다. 1차 대여에서 이 stage 가 "통과"로 보였던 것은 solver 가 없어 `check_batch` 가 spawn 자체를 하지 않고 즉시 error 를 반환했기 때문이고, 실제로는 검증된 적이 없다.

### stage 6 진단: vtune threading 수집 불가

`intel-oneapi-vtune` 2026.4 설치 자체는 됐지만(sepdk 드라이버 빌드까지 완료, `pkg-config` 부재 경고 하나) `-collect threading` 이 세 번 모두 `Error: 0x4000001e (Cannot load raw collector data)` 로 끝났다. 짧은 타깃(`--quick`, 0.5s)과 60초 루프 타깃 둘 다 실패했고, 60초 루프판은 계측 아래에서 15분이 지나도 끝나지 않아 강제 종료했다. 쌍마다 solver 프로세스를 fork/exec 하는 워크로드라 threading 수집기와 궁합이 나쁘다. **스레딩 분석은 WSL/hotspots 기준선을 그대로 둔다.** 이 항목은 대여로 얻을 수 있는 것이 아니었다.

### 남은 차이 하나

ctest 총 개수가 1차 303 개, 이번 266 개다. 이번 이미지는 clang 18 / cmake 3.28, 1차는 clang 14 / cmake 4.4.2 였다. 두 실행 모두 실패 0 이지만 등록되는 테스트 집합이 도구 버전에 따라 달라진다는 뜻이므로, 어느 쪽이 정본인지는 로컬에서 한 번 맞춰봐야 한다.
