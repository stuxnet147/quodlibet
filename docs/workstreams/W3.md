# W3. 런타임 서비스: 로깅, 예산, 판정 정책

브랜치: `w3-runtime-services`
담는 GOAL: G1, G2, G3
진행 기록: `docs/workstreams/W3-progress.md`

**시작하기 전에 `docs/workstreams/README.md` 를 읽습니다.**

## 이 워크스트림이 지는 것

Quodlibet 이 남의 프로그램 안에서 도는 라이브러리가 되려면 셋이 있어야 합니다. 무슨 일이 있었는지 말할 수 있어야 하고(로깅), 얼마나 쓸지를 호출자가 정할 수 있어야 하고(예산), 무엇을 합격으로 칠지를 호출자가 정할 수 있어야 합니다(판정 정책).

셋 다 **호출자가 세밀하게 정한다**는 것이 요구입니다. 기본값 하나로 때우지 않습니다.

## 소유하는 파일

- 새로 만들 것: `src/log.c`, `src/budget.c`, `src/policy.c` 와 `include/quodlibet/log.h`, `budget.h`, `policy.h`
- `src/allocator.c`, `include/quodlibet/allocator.h` (메모리 예산 계측이 여기 붙습니다)
- `third_party/` 중 새로 벤더링하는 로깅 라이브러리와 `third_party/CMakeLists.txt`
- `DEPENDENCIES.md`
- 새 시험들 (`tests/test_log.cpp`, `tests/test_budget.cpp`, `tests/test_policy.cpp`)
- `docs/workstreams/W3-progress.md`

`src/scheduler.c` 와 `src/pipeline.c` 에 예산 훅을 넣어야 하면 **최소 변경으로** 하고 진행 기록에 적습니다. 두 파일은 지금 아무도 확장하지 않으므로 충돌 위험은 낮지만 기능을 늘리지는 않습니다.

## G1. 로깅

**직접 만들지 않습니다. 외부 라이브러리를 벤더링해서 배선합니다.**

### 선정

후보를 비교하고 고른 근거를 `DEPENDENCIES.md` 에 적습니다. 비교 축은 이렇습니다.

- **라이선스.** MIT, BSD, Apache-2.0 같은 permissive 여야 합니다. LGPL 은 정적 링크 배포에서 문제가 되므로 피합니다
- **언어.** 코어가 C17 입니다. **순수 C 라이브러리가 강하게 선호됩니다.** C++ 라이브러리를 고르면 정적 라이브러리 소비자가 C++ 런타임을 링크해야 하므로 그 대가를 명시하고 조율자에게 먼저 말합니다
- **비활성 레벨 오버헤드.** 꺼진 레벨의 호출이 얼마나 싼지
- **스레드 안전성.** 워커 풀에서 동시에 기록해도 줄이 섞이지 않아야 합니다
- **크로스플랫폼.** Windows 와 Linux 둘 다
- **크기.** 이 저장소는 작고 고정된 dependency 를 벤더링합니다. 거대한 것은 맞지 않습니다

벤더링은 `scripts/vendor.sh` 의 기존 방식을 따릅니다. **SHA-256 고정**이고 configure 중에 네트워크를 타지 않습니다.

### 배선

- 공개 C API 로 레벨(최소 trace, debug, info, warn, error, fatal)을 런타임에 설정
- 상세도를 축별로 설정: 소스 위치, 스레드 id, 타임스탬프와 그 정밀도, 카테고리 또는 서브시스템
- 싱크를 호출자가 줄 수 있게 합니다. 라이브러리가 남의 stdout 을 마음대로 쓰지 않습니다
- 공개 ABI 구조체는 `struct_size` 와 `abi_version` 을 답니다
- 기본값은 **조용한 것**입니다. 호출자가 켜야 나옵니다

### 측정

**비활성 레벨 호출의 오버헤드를 실제로 재서 수치로 적습니다.** 호출당 나노초입니다. 추정하지 않습니다. 재는 방법도 같이 적어서 나중에 다시 잴 수 있게 합니다.

## G2. 실행 예산과 메모리 예산

### 실행 예산

축이 셋입니다. 각각 따로 설정됩니다.

- 전체 wall-clock 상한
- 파이프라인 노드별 상한
- solver 호출별 상한 (`SOLVERS.md` 에 이미 solver 쪽 deadline 이 있습니다. 그것과 이 축을 어떻게 합칠지 정하고 적습니다)

### 메모리 예산

- 전체 상한
- 할당자 계측: 현재 사용량과 최대 사용량
- **초과하면 할당이 결정적으로 실패합니다.** 무작위로 어디서 실패하는 것이 아니라 상한을 넘는 순간 실패하고, 그 실패가 호출 경로를 타고 깨끗하게 올라옵니다

`src/allocator.c` 가 이미 할당자 간접층입니다. 여기에 붙입니다.

### 넘지 않는 선

**예산 초과는 논리 판정이 아니라 상태입니다.** 예산을 넘긴 실행이 `PROVED_*` 나 `COUNTEREXAMPLE` 을 내면 안 됩니다. `BOUNDED_CLEAN` 으로 새는 것도 안 됩니다. 예산 초과로 끝난 실행의 결과는 `ql_status` 오류이거나 `UNKNOWN` 입니다. **이것을 시험이 고정합니다.**

예산 초과로 중단된 실행이 이미 만든 artifact 를 전부 해제해야 합니다. ASan/UBSan 프리셋에서 확인합니다.

## G3. 사용자 정의 검증 결과와 판정 규칙

호출자가 **어떤 증거가 어떤 판정을 정당화하는지**를 JSON 으로 정의합니다. 예를 들어 강화학습 보상으로 쓸 때는 "proof 만 합격", 빠른 필터로 쓸 때는 "bounded clean 도 통과로 표시하되 그 사실을 결과에 남긴다" 같은 것입니다.

- 버전이 있는 스키마입니다. `precondition_json` 의 `schema_version` 방식을 따릅니다
- 파서가 잘못된 정책을 **실행 전에** 거부하고 오류 위치를 말합니다
- 결과 직렬화도 정의된 스키마를 따르고 그 출력이 다시 파스됩니다(왕복 시험)

### 정책이 넘을 수 없는 선

**정책은 코어의 건전성 규율을 약화시킬 수 없습니다.** 다음을 시도하는 정책 JSON 은 파서가 거부합니다.

- `BOUNDED_CLEAN` 을 `PROVED_*` 로 올리는 것
- replay 하지 않은 SAT model 을 `COUNTEREXAMPLE` 로 올리는 것
- raw solver `UNSAT` 을 checker 나 명시된 trusted-backend policy 없이 `PROVED_*` 로 올리는 것

정책이 할 수 있는 것은 **이미 정당한 판정들 중에서 무엇을 합격으로 셀지**를 정하고 그 이름을 붙이는 것입니다. 판정 자체를 만들어내는 것이 아닙니다. 이 구분을 `METHODS.md` 나 새 문서에 적습니다.

W2 가 실제 판정을 만들고 있습니다. 판정 종류는 `include/quodlibet/semantics.h` 의 verdict 열거형이 이미 정의합니다. **그것을 읽고 쓰기만 합니다. 고치지 않습니다.**

## 종료 조건

`GOAL.md` 의 G1, G2, G3 전문입니다.

## 하지 않는 것

- C 로어링과 IR 은 W1, SMT 백엔드는 W2 입니다
- 파이썬 바인딩은 W4 입니다. 다만 **예산과 정책이 나중에 파이썬에서 노출됩니다.** 구조체를 설계할 때 그것을 염두에 둡니다
- scheduler 와 plugin 기능 확장은 하지 않습니다. 예산 훅만 넣습니다
